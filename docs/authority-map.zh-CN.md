# 权威归属

这份文档回答一个问题：**每一个事实由谁产生、存在哪里、谁消费、能不能派生。**

它存在的原因是一次自我诊断：在连续几轮修缺陷之后，我们发现自己**在按症状打补丁**——
每条失败加一个分支、每个分支加一个字段、每个字段再加一条断言。断言数在涨，
可靠性没涨。根因不是某一条判据写错了，而是**同一件事被两处各自推断了一遍**：
宿主已经在回答进程事实，我们又在内存表里推一遍；投影已经算出状态，不变量旁边又建了一套解释器。

**一条纪律**（本文的验收标准）：

> 同一类故障只需要在**一个地方**解释；同一件事实只有**一个权威来源**；
> 同一次运行**不会因为一次读取失败而被重复执行**；没有证据时系统能**安静地说不知道**。

## 一、三个plane，各有各的事实

| 事实 | 权威 | 我们怎么做 |
|---|---|---|
| 子任务是否被接受、在跑、已结束；结束原因；会话是否在运行；是否该继续调度；哪次审批真的由人作出 | **DSH 宿主** | 消费。`subagents.listChildren`（`activity: running / inactive`）、`subagent/end`（`stopReason` + 收尾消息）、`agent/turn-stopping` / `agent/error`、持久化会话日志——**它们是同一事实的不同读法，不是三套竞争的真相**。 |
| 要检验哪个命题；事先承诺了什么判据；哪份观测用于哪次评估；哪次评估支持/推翻/无法判定；一条事实为什么获得或失去可引用资格；人在哪个问题上做了什么决定 | **ClearAI** | 这是不可替代的那部分。任务完成 ≠ 命题成立；评估失败 ≠ 命题被推翻。 |
| 文件当时是什么内容 | **Git 账本** | 只回答"当时是什么"。**不能**单凭路径回答"它如何产生、是否可信"。 |
| 界面显示的"在跑/已可信/等人" | **投影（派生）** | 不另存第二份判断：从上面两类事实现算。 |

### 一条推论（上一批写错过的）

**父回合结束，只证明父回合结束。** 它不证明子任务再也不会回来：
子任务可能仍在宿主里跑，也可能**已经结束、结论还没被收集**。只有宿主明确报告结束/失败，
才谈得上对应判断。因此：

| 观察 | 正确的理解 |
|---|---|
| 父回合结束，子任务仍在跑 | 等宿主后续结果；**不自动重派** |
| 子任务已结束，结论尚未进 ClearAI | **收集同一次运行的结果**，不重新执行 |
| 子任务失败 | 记录失败；要不要重试是下一次决策 |
| 评估结束但评估卡落盘失败 | 运行已结束、文件落盘失败——**不能让账本看上去像评估还在进行** |
| 宿主当前查不到运行状态 | 状态**未知**，不等于已经死亡 |
| 两份读数不能证明采用同一测量标准 | 可以展示原始读数，**不能宣称存在有效的数值排名** |

## 二、已经证实的四条（都指得出代码）

### ① 收尾那一拍宣告了它没有核实的事（已确认为**表述错误**）

宿主的 `agent/turn-stopping` 上，我们会在运行态卡里写：

> 上一个回合结束时还有 N 条子 run 仍在飞——**它们的结论不会自己回来**（要么重派，要么把对应那一步作废）。

"仍在飞"是**当时我们内存表里看到的样子**；"结论不会自己回来"是**推论**，而它没有证据：
子任务可能仍在跑（宿主稍后会报告），也可能已经结束、结论只是还没被收集。
而且——**内核本来就会问宿主**：`sweepLostScouts` / `sweepLostAudits` 都读
`subagents.listChildren` 的 `activity`，那才是"还在不在跑"的权威答案。收尾那一拍没用它。

**结论**：这句话必须退回成"当时快照"，或者（更好）改成去问宿主。**不是**再加一个字段。

### ② 评估者没有"结束但未收集"的回收路径，侦察有（已确认为**不对称**）

- 侦察：`sweepScouts` 先看进程里的句柄，**读不到就回过头去读子会话自己的日志**
  （`recoverFromChildSession`）——"孩子结束了但结论没送到"能被捞回来。
- 评估：`sweepLostAudits` 只看两件事——投影里 `verdict === null`、且这个 child 不在我们内存表里、
  且宿主说它 `activity !== 'running'`——然后就写：

  > 评估者失联:派它的那次进程已经不在了,子会话也不在跑——**这次裁决不会有结果**。

  从"不在跑"推不到"不会有结果"：**子会话可能已经正常结束，裁决就在它的日志里**。
  更糟的是这一步之后模型被引导"重新交付这一步会派一个新的评估者" ⇒ **同一次评估被重做**，
  而原来那份结果可能就躺在盘上。

**结论**：这类缺陷的正确形状不是"再补一条收尾扫描"，而是**给评估者与侦察同一条回收路径**：
先试着取回同一次运行的结果，取不回来才写结算事实，并且把理由写准
（`ended_uncollected` 与 `lost` 是两件事）。

### ③ 尺子的"口径"检查是**格式检查**（已确认为**能力被夸大**）

`ForkPlan` 现在要求 `decide_by.metric` 写成「量 = 口径」。它保证的是：**声明被登记、被逐字传给
每条世界线的判据与任务书**。它**不**保证两条读数真的可比：

```
评分 = 按本路线情况评分        ← 同样通过检查
```

**结论**：这项机制的价值是"把口径从各写一套，变成一份声明、人人可见"。
文档与真值表里凡是把它说成"共同测量标准由构造保证"的地方，都要改回它真正做的事，
剩下的交给评估者重跑（那也是唯一能真正确认的办法）。

### ④ 宿主不变量伴生件正在长成**第二套解释器**（已确认为**结构问题**）

`ui/lib/invariant.js` 为了"在落账之前判"，自己折叠了 plans / steps / forks / branches /
admissions / dispatches / scouts / audits / hypotheses / support levels 一整套索引。
它上岗第一小时就因此被修了两次（变更常常只带 `step` 不带 `plan`；目标轴与世界线轴用的是伪步骤），
两次都是"我的解释器与主投影不一致"，而不是"业务真的有错"。

**结论**：宿主提供注册机制 ≠ 所有业务规则都适合变成落账前的硬拦截。
这个伴生件要按下面的界线重新裁一次（见 §四）。

## 三、重复承担职责的地方（复审对象）

| 我们维护的 | 宿主/投影已有的 | 它**唯一**不可替代的贡献 |
|---|---|---|
| `scoutRuns` / `executorRuns` / `pendingAudits`（内存表） | 宿主：`listChildren.activity`、`subagent/end`；投影：`scout/dispatched`、`worldline/executing`、`audit/dispatched` | **业务绑定**：这个 child 是哪条世界线/哪次侦察/哪一步的评估；以及本进程攥着的结论句柄 |
| `turnEnds`（投影里的回合收尾） | 宿主：`turn/end{reason}`；`subagents.listChildren` | 几乎没有——它是"当时我们看到的快照"。要么删掉，要么只留"账本在这一刻记了一笔工作区" |
| `invariant.js` 的轨迹索引 | 折法（`fold.js`）已经算出的状态 | 只有"落账**之前**"这一个时机价值；索引本身是重复实现 |
| `lastWorkspaceSnapshot`（写入计数 → 快照） | Git 账本自己 | "哪一次写入之后落过账"——但账本本来就有提交历史，这一格可以只留去重 |

## 四、规则该硬拦还是该诊断（重新划界）

**"越早拦越好"是错的。** 界线应该是：

| 类别 | 处理 | 例子 |
|---|---|---|
| **非法业务操作** | 工具入口拒绝 | 模型冒充人作审批、没有判据就交付 |
| **已经发生的运行失败** | **必须允许记录** | 评估者崩溃、评估卡落盘失败、子任务被打断 |
| **历史记录自相矛盾** | **报告诊断，保留原始记录** | 引用不存在的步骤 |
| **无法证明的业务判断** | 标为未知，交给评估者 | 两条读数是否可比 |

> 不能让"维护账本的一致性"变成"**只允许好看的事实进入账本**"。
> 一条已经发生的失败被拒收，本身就是一次不实陈述。

## 五、接下来怎么做（不改代码的架构复核）

1. **从真实轨迹重建因果链**：挑三类轨迹——正常完成、评估失败、父回合结束但子任务未结束——
   逐次把「运行 ID → 派遣 → 结果 → 业务落账」串起来，**区分已证实原因与猜测**。
   依据是 `~/.dsh/e2e-archive/` 里的会话日志原件与 `docs/optimization/e2e-logs/` 的解码件。
2. **填完这张归属表**：每个字段写清谁产生、存哪、谁消费、能否派生。复审对象是 §三 那四行。
3. **给出保留／删除／委托宿主的方案**，**对最近四个未发布的提交一视同仁**——
   不因为是我刚写的就默认值得留。优先删除错误推论、重复状态与不成立的硬拦截，
   再决定是否需要新增代码。

验收标准用 §〇 那一条，**不是**"又多了多少条断言"。
