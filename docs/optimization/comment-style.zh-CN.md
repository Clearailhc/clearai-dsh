# ClearAI 注释风格

> 这份文件是**可引用的判据**。`test/comment-style.test.mjs` 按它做机械核对；
> 人审也按它判。它约束的范围是 `preset/plugins/*.js` 与 `ui/lib/*.js`（代码注释），
> 不约束 `docs/` 下的正式文档。

## 规则

一条注释只写三件事，**按需要写，不要求全写**：

1. **为什么这样做** —— 这个选择换来什么、拒绝了什么。
2. **不这样做会怎样** —— 具体的失败模式。**不带日期，不带事故编号。**
3. **边界在哪** —— 什么条件下这套不成立、什么情况下必须改。

## 禁止

| 禁止 | 为什么 |
|---|---|
| 日期戳（`2026-09-11`、`2026-09 对齐`） | 读者不需要知道这件事发生在哪天；需要的人去查 git |
| 内部章节号（`§34`、`§17.6`） | 本仓库没有章节号对照表，它指向一个读者查不到的地方 |
| 事故叙事（「长测」「实测」「现场」「用户抓到」） | 它把注释变成事故报告；**失效模式本身**才是有用的信息 |
| 变更流水（「原先…现在…」「阶段 N 已修正」） | 这是 `CHANGELOG` 与 git 的职责 |
| 被删代码的历史 | git 就是历史账本。注释不是 |

一句话判据：**把注释里所有时间与事件都拿掉，它的结论还成立吗？**
不成立，说明写的是历史；成立，说明写的是理由——只有后者该留在代码里。

## 正例

```js
/**
 * 计划授权必须是"人按的那一下"。
 *
 * 只有原生审阅卡返回 approved 才写 confirmed_by='user'——如果让系统自己签这个记号，
 * 后面所有基于授权的推理都是空的（分不清"人批准过"与"系统认为人会批准"）。
 *
 * 注意它**不是硬阻断**：未授权只让自动续跑 hold，交付一步会在同一条变更里补写
 * confirmed_by='progress'。所以这个记号表达的是**归属**，不是闸门。
 */
```

为什么它合格：第一段给理由与代价，第二段给替代方案会坏在哪，第三段给出边界。
没有日期、没有章节号、没有"原来是这样"。

## 反例

```js
/**
 * 计划永远要人确认(§34):原先无人值守那一档「立约即授权」✗——
 * 那会让「计划经人确认」这条证据变成系统自己签的。
 * 2026-09-11 长测现场:模型因此停下来问过人。
 */
```

为什么它不合格：读者不知道 `§34` 是什么；`原先…` 与日期戳把变化过程写进了代码；
「长测现场」是事故编号而不是失效模式。**把这三样拿掉之后，剩下的那句话才是真正该写的**。

## 棘轮

清理不是一次性动作。`test/comment-style.test.mjs` 为四类反模式各维护一个**基线配额**，
配额只能降不能升：

- 加了新的反模式注释 ⇒ 测试红（配额被顶破）；
- 清掉一批 ⇒ 顺手把配额调低（在测试里改那个数字，并在提交信息里说明）。

于是"还没清完"是一笔**有账的债**，而不是"没人管"。阶段 9 的目标是把配额降到 0。

## 与「保留历史」的关系

本项目的 P5 是「什么都不删」——那说的是**系统的行为记录**（被推翻的假设、作废的步骤、落选的世界线）。
代码注释不是行为记录：
**系统的历史进账本，代码的历史进 git。** 两者都不该抄进注释。
