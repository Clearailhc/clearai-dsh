## 发现

1. **提示词收成三段之后,主链照样一次走通。** 三场的模型都先 `Frame`(`headline` 都在 120 字内,每场两条带推翻条件的判断)、再 `CreatePlan`、逐步 `AdvancePlan`、`ClosePlan`、`Conclude`。
   竞争路线把比较那一步同时列上两条判断,一支持一推翻;证伪那场一条推翻、一条支持;长链事先登的「两条路径会不一致」被推翻。没有一次交付或结案因为不懂规则被拒。
2. **答复的形状变了。** 三份最终答复都按「结论 / 凭什么 / 适用范围 / 被推翻的 / 还没定的」写(第四阶段三份里只有一份带「适用范围」这类小节),
   并且主动交代证据等级不够、没有升格的判断。这是「对人说话」那一段直接管的东西。
3. **模型没有为了消缺口去造词。** 三场的判断都是纯文字,卡上挂着 `prose_only_claims`;竞争路线的模型在答复里明说这是单次的小比较,不另立术语。
   这正是循环段那句「别为了消掉缺口造词」。结果是实体门与升格在这三场里都没被考到(三场都是 L2 自判,没有判断到 L3 门槛),与第四阶段第一场证伪相同;门本身由 `test/kernel.test.mjs` 覆盖。
4. **机器名还有残留。** 证伪那场的答复仍写出 `h-pow5bc`、`support / refute`。提示词已经要求不用机制名,但运行态卡和工具结果里满是这些词,模型会照抄。
   卡与工具结果说人话属于第六阶段(呈现)。

## 测试台本身(这次出了一次故障)

- **评估者派晚了。** 盯挂起请求的脚本按紧凑 JSON 去匹配 `--pending` 的输出,而它是带缩进的,于是三场结案时的评估请求都没被发现,
  晚了十几分钟才派评估者。三场的第一次 `Conclude` 都在 900 秒处超时,返回「目标评估者仍在跑……先观察当前事实,再谈重试」,目标保持开放。
- **内核的处置是对的。** 超时没有把评估作废,也没有重派:三场都只有一次 `audit/dispatched`、一次 `audit/settled`。评估者晚交的裁决照样落账,
  第二次 `Conclude` 直接取用了它。所以每场多出的那 1 次调用是测试台造成的,不是提示词或机制。
- 三位扮演模型都没有自己宣布完成。证伪那场的模型看到目标还开着,自己再交了一次结案;另两场停下来问人要不要重交,由编排者告诉它们重交一次。
- 三位评估者都给出了结构化裁决并用 settle 交回。竞争路线的评估者多用了一次只读的 `cat`(任务书只允许 settle 这一条命令),它在报告里如实说明了。
