# 供应链追溯对照：DSH 原生与 ClearAI

2026-11-07。本案例的结论是：**两组的核心图谱和业务计算均准确；ClearAI 形成了更丰富的结构化沉淀和独立裁决，也付出了更高成本，且变更阶段在评估前耗尽预算。现有结果不支持“整体优于原生”或立即发布。**

真实官方 DSH 0.2.2-rc.1 会话及 DeepSeek API，模型 `deepseek-flash / medium`，业务资料为合成数据。原生 default 保留正常工具、子任务、笔记和文件能力，不是纯文本裸模型。两组任务和资料相同，各阶段新会话只保留自己的工作区。协议见 [traceability-protocol.md](traceability-protocol.md)，核对摘要见 [traceability-receipt.json](traceability-receipt.json)。

题目提供八种类型、七种关系字典，检验多来源对齐、本体实例化、追溯查询、证据边界与变更维护，不证明从零发现本体的能力。每场上限 1,000 万处理 token、180 分钟、估算 $10；沿用累计 $60 账本，不重置历史支出。

|可复用程序|查询、图谱构建、检查、历史 as-of 快照|分析、SQL 交叉检查、查询、图谱构建、阶段快照|
|历史保留|阶段 1/2 报告字节保留|阶段 1/2 报告及旧事实文件保留|

ClearAI 扩展对象包含通知、返工、退货、隔离决定和待验证说法。所有导出实体与边均有可定位来源；核心对象的引用与控制器答案逐条一致。扩展对象需要单独判断语义，不能把原始评分中与核心集合不重合的部分直接算错误，也不能把有来源自动当作独立认证。最终图谱与平台内部实体/断言覆盖一致。

第一阶段的三条事实分别承载 18 条出货断言、12 条隔离/放行断言、4 条证据边界断言。第二阶段虽新增四条文字事实，结构化断言总量仍为 34。会话视图中的“当前事实数”和工作区累计事实数不同，不能据此误判丢失。

两组都有实际复用行为：原生读取并扩展旧脚本与 as-of 快照；ClearAI 第二阶段读取事实索引及已有事实，评估者检查事实文件，第三阶段读取事实索引并引用旧产物。**独立副本执行最终脚本，两组均准确复现三个阶段的批次、逐笔净额与客户汇总。** ClearAI 第三阶段的离线复现是产物验证，不补记为原任务完成。

另有复用声明不准确：ClearAI 阶段 2 的 `analysis/out/phase1_submission.json`、阶段 3 的 `analysis/out/phase2_submission.json` 都是当阶段才创建的快照，不能算作该阶段启动前已经存在的复用文件。其余列明的先前产物存在性已核查。没有冷启动消融，因此不声称复用节省了多少 token 或时间。

其他宿主调用另列在机器摘要；评估等待期间没有主模型轮询。

第一阶段先做声明审计，再做目标审计，两次都成功，不是评估失败后的重试。第一次发现扩展图谱的返工放行边与报告表述问题，主代理随后修正、补充 rework_for 关联并重建。核心三项业务结论获得独立支持。目标审计随后又从原始 CSV 重算隔离与暴露。两次材料摘要不同，因此不能假定整次重验都应取消；应针对未变的局部依赖保留裁决。

还有两次派评前本地拦截：假设名称与 ID 混淆、缺少断言关联。它们增加主代理往返，但没有启动额外评估者。第二阶段只做一次目标审计，仍然较慢。第三阶段所有预算主要耗在主代理，尚未进入评估。因此本例不支持“主要只因派评频繁”的单一解释。

人工检查另发现语义弱点：ClearAI 的 rework 定义和报告添加了“有 release_document 才放行”的条件，正式通知和数据字典只明确批准、完成时点和产品例外。当前脚本未据此错误排除批次，数据也未触发数量差异，但不能把这条额外条件当作已证明的复用规则。独立评估通过不代表所有扩展定义都被穷尽证明。

## 本例支持的优化顺序

1. **先减少主代理的重复搬运和自查。** 业务记录、图谱导入、类型/引用/单位/历史完整性使用可重跑的确定性检查，并把检查版本、输入摘要、输出摘要作为证据。审计仍应验证检查方法及关键反例；不能把工具成功直接当成结论成立。只传当前任务需要的差异与证据入口，避免反复展开全量代码、历史和图谱。
2. **将独立裁决绑定到最小完整依赖。** 同时记录命题、范围、源记录、规则/程序版本、信任条件和未决问题。局部关系或文字修正时，重验其影响闭包及未覆盖目标；依赖变化或不完整时保守重验。保留已支持的独立子结论，不将其因无关修改重新打回。
3. **让最终交付优先走一次合并审计。** 没有中间决策需求时，把待落库声明与目标验收交给同一审计；需要中途独立判断时保留独立派评。改善 ID 引用和断言预检，减少低价值往返，不放宽来源、范围和反例标准。
4. **把知识质量纳入验收。** 区分源记录、规则、推导结果、假设和独立事实；不增加来源没有的条件。同时衡量核心覆盖、扩展语义、结构化断言、可运行复用和变更后的适用性，不以事实文件数或节点数单独排名。

以上是基于观察的下一轮方向，不宣称本次已经实现细粒度依赖复用或证明其节省效果。

## 保留的兼容失败、修复与账本

最初 ClearAI 使用产品 `57c13d5`，包摘要 `a64e472069ea437e75b469cd45cf2e13c4b42fce39b2500aaab0554f19f98211`。第一阶段产物的核心数据准确，但 DSH 输出 schema 不支持 `minItems`，评估无法启动，目标未闭合；后两阶段跳过。失败消耗约 345 秒、2,900,274 token、$0.099187，不从记录删除。

修复 `d1b75ba` 将数量约束转换为宿主支持的说明，内核继续检查声明数量和覆盖完整性；回归直接调用官方 DSH schema validator。修复安装包 `75fd4f42977d3268dd5188e3769504c42fe20b79439a317658cb46112d8cf976`，仅补跑同一冻结题目的 ClearAI，原生不重跑。完整安装件回归与 45 项发行包检查通过；本题生成/评分两项测试通过；修复后的真实评估成功启动和完成。

本轮含原生、修复后 ClearAI 及最初失败，共 **$1.280273**；累计账本 **$8.546875 / $60**，其中含此前已接受的 $0.80 历史未知预留。当前 pending=0，新增未知费用=0。

## 交付与边界

产物包含两组每阶段的合成源数据、图谱、脚本、报告、知识文件，以及 manifest、结果与核对记录；不含 API key、控制器私钥或模型私有推理日志。原生第三阶段额外生成的 query-phase3.json 补充进交付包，保持脚本可执行。

这是单案例、每阶段一次的诊断对照。原生先前与故障 ClearAI 并行、修复组随后运行，时段和并发不同；没有多次抽样或冷启动消融，不外推统计优势。未进行发布，也不建议凭这次结果发布 0.6。
