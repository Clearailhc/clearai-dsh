## 本轮修改及权限边界

- 主代理保留原生读写；`ReadEvidence` 普通读取始终返回原文。显式条件读取只省略本会话已经完整收到、范围和字节均未变化的文本。修改文件、新范围、新会话、部分截断均重新返回文本；上下文压缩后可普通读取恢复。
- 评估者不继承主代理读取回执。直接写工具禁用，要求在隔离副本复跑，副本修改不回写主工作区；结算校验发现引用材料变化时拒绝落账。这是工具与裁决权限边界，不是操作系统文件系统沙箱。原生 shell 的所有副作用并未因此被强制禁止。
- 主代理自己的工具结果进入其上下文；外部修改不被假定为已知。评估者返回问题、证据位置和修复建议，由主代理处理。
- Frame 返回精确假设 ID，并提前提示结构化断言的关联缺口；保留原有核验标准。知识概览区分当前事实、已加载事实、待复核事实、事实内断言与实体文件记录。
- 文件来源标记基于会话首次工具调用前的有界观察，不推断任务前存在性。未知来源保持未知，不能作为正确复用的证明。

其他宿主调用另记；等待评估期间主模型轮询为零。第二阶段主代理请求耗时约 718 秒，评估约 1016 秒。主代理处理 token 占多数，评估输出及耗时也很重，不能归结为一个原因。

第二阶段第一次目标审计的数值判据全部通过，失败理由是第一阶段报告与第一阶段审计摘要不同。实际记录显示：

1. 第一阶段审计时报告为 291 行，摘要前缀 `9ade848f`。
2. 第一阶段审计通过后，主代理改写第 149 行并新增质量注记，最终报告为 301 行，摘要 `87d948a37422fe435afa6e09510da57901a293d18c4e36317a366d1d1722a367`。
3. 第二阶段报告与第一阶段最终快照逐字节相同。第一次评估把“审计时版本”当成“上一阶段最终版本”，在历史保留判据上用了错误基线；同时，审计后的补充确实没有被原审计摘要覆盖。
4. 主代理登记差异、补充结构化关联，先核验改动，再另行核验查询结果，两次证据审计均通过，最终目标却未能在限额内收束。

这不是三个完全相同的请求。后续增加了结构化断言和材料，不能按请求重复直接跳过。问题是缺少清楚的版本交接、差异证据与已支持子结论的衔接，导致模型重建时间线、反复复跑和重新表述。

语义抽查另发现：导出图谱把供应商定义为“法人”，但事实 `f-lg6qva` 明确说资料不足以判断法人关系。源 ID 权威性并不自动证明法律身份。数值和来源定位检查通过，不代表所有定义都忠实于证据。

## 条件读取是否真正节省

旧题第一阶段主代理、评估者均未用 `ReadEvidence`。第二阶段主代理未用，评估者调用 4 次，读取 10 个来源；条件命中为 0，省略字符为 0。因此本轮没有观测到该功能带来的重复传输节省。

确定性工具实验中，180 行示例原文的 JSON 输出为 17,225 字节，条件命中回执为 407 字节，普通读取能恢复原文。这只证明传输行为正确，不是实际任务 token 节省。工具存在与模型采用率必须分开验收。
