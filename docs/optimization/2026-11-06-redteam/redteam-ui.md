# ClearAI UI / 可读性红队评估

日期：2026-11-06。对象：当前 ClearAI 0.5.7 源码与本轮生成的 dist 客户端。评估者独立于兼容性修复；本报告未修改应用代码。

## 结论

视觉语言克制，组件采用宿主色彩令牌，探索/本体分层和显式状态标签有价值；但“能画出来”与“便于理解、能完整操作”存在显著差距。当前不宜宣称键盘可访问或窄屏可用。主要问题是可交互元素不进入 Tab 顺序、全屏抽屉挤掉画布，以及自动适配把中等规模图谱的文本缩到不可读。

本轮不作脱离场景的单一美观分数：桌面少量节点的界面比较整洁，中等密度与窄屏的任务可用性明显较差。

## 优先发现

### P1 — 关键阅读路径对键盘用户不可达

**证据强度：浏览器 DOM 实测 + 源码确认。**

在 1280 与 375px 页面，“本体图”“实体图”“适配”“全屏”全部是 `SPAN`，`role=null`、`tabIndex=-1`。源码没有相应键盘处理。Tab 无法进入切层和全屏入口，不能用标准键盘操作获得同等能力。结论详情与来源也是核心认识论可审计性的一部分，不应只给鼠标用户。

对应源码：

- `ui/lib/client.js:2749`–2750：两种图的切换是点击 span。
- `ui/lib/client.js:2761`–2762：适配和全屏是点击 span。
- `ui/lib/client.js:535`：通用 `Link` 返回点击 span。
- `ui/lib/client.js:992`：结论展开是点击 div。
- `ui/lib/client.js:2349`–2350：Inspector 的过滤和关闭是点击 span。
- `ui/lib/client.js:260`：图节点 `:focus` 被明确设为 `outline:none`；没有同一规则的替代焦点圈。应在真实键盘流程中补验焦点是否始终可见。

**建议**：按钮用原生 button；导航用语义正确的链接；图层选择采用按钮组或完整 tabs 模式；结论展开提供 `aria-expanded`、可聚焦触发器；保留明显 focus-visible。补真实 Tab/Enter/Space/Escape 测试，而不是只断言 React 树存在 onClick。

### P1 — 375px 全屏打开详情会令图谱消失，详情关闭区被截断

**证据强度：真浏览器几何与截图复现。**

`.clearai-graph-body[data-side="1"]` 固定横排，详情宽 380px 且不能收缩，全屏左右又有共 40px padding；缺少窄屏切换布局。

测量结果：375px 视口，canvas 宽 **2px**；inspector x=32、宽 **380px**、right=**412px**。截图中画布只剩左边一条线，抽屉右侧操作超出画面。该结果不依赖 inspector 内容；空响应照样挤压。

对应源码：`ui/lib/client.js:222`、233、255、2729。证据：`ui-fullscreen-375.png`、`ui-metrics.json` 的 `375-fullscreen-inspector`。

**建议**：按容器宽度折成上下布局或独立详情覆盖层；抽屉 `max-width:100%`；关键操作固定在可见区域。验收 320/375/768px 及浏览器 200% 缩放；确认打开详情后图仍可导航、关闭可达。若产品只支持宽屏，应明确最小宽度并给出受控降级，而不是压到 2px。

### P2 — 中等图谱自动 fitView 导致文本极小，“完整显示”牺牲可读性

**证据强度：真浏览器构造数据实测；不代表真实使用频率。**

1280px 视口下，50 个有长中文标签的节点和 49 条边（10×5 排布），默认适配得到 `scale(0.465974)`；节点字体 CSS 为 12.5px，实际约 **5.82px**。边标签原字号 10px，实际约 **4.66px**。截图中虽然所有点都出现，用户无法舒适扫读。历史 JEPA 截图也可见类似极小标签，但该截图版本较旧，只作旁证。

源码：`ui/lib/client.js:261` 节点字体；2614 附近边标签 10px；2709–2712 在全屏/图层/选中状态/节点数变化时自动 fitView；2788 附近 minZoom=0.2，理论可将节点字号压到 2.5px。

证据：`ui-dense-1280.png`、`ui-dense-dark-1280.png`、`ui-metrics.json` 的 `50-long-labels`。

**建议**：默认局部导航/聚类摘要，缩小时减少标签而非把全文缩小；提供可搜索的文本目录和明确“聚焦所选”操作；新数据到来不要无条件重置用户缩放。设定可读性场景而非节点计数性能阈值，例如 50/200 节点下能找到指定概念、读清关系、返回来源。

### P2 — 中文图里的辅助技术说明仍是英文

**证据强度：浏览器 DOM 实测。**

中文页面 DOM 内有 React Flow 默认说明 `Press enter or space to select a node... Press delete to remove it...` 和英文 edge 说明。`ui/lib/client.js:2778`–2800 的 ReactFlow props 未提供 `ariaLabelConfig`。可见 UI 双语不代表辅助技术也双语；同时“delete to remove”与产品只读叙事容易冲突，应核实工具允许的本地操作并同步说明。

**建议**：接入宿主 locale 为图控件与读屏描述本地化，明确选择/移动/删除的实际能力；增加 zh/en 两种语言的可访问树检查。尚未用真实读屏器听测，不声称其最终读音顺序已确认。

### P2 — “可读性测试通过”覆盖范围不足以支持 UI 可读性主张

**证据强度：测试源码审计。**

`test/readability.test.mjs:1`–20 的目标主要是运行态卡长度、nextAction、判据映射、词典、概念分类；其价值真实，但没有验证人类在屏幕上的字号、换行、键盘路径、视觉信息负担。`tools/browser-graph-check.mjs` 只确认模块装载、绘制和拖动：本轮它全绿，同时上述 P1/P2 仍成立。

**建议**：把“内容结构检查”“图谱渲染检查”“人工任务可用性检查”分别报告，避免总称“可读性全绿”。用定位证据、识别待验证状态、找到反例、解释冲突等用户任务衡量完成率和时间。

## 正面证据

- 原浏览器图谱检查 **9 项均通过**：客户端工厂按宿主 require 契约物化，未降级，React Flow、节点、边、Controls/Background 出现，样式注入，真实鼠标拖动成功且重渲染不复位。
- CSS 使用宿主色彩令牌，代表性浅/深主题下文本和控件随之变化；没有再次观察到白底白图标的问题。
- 明确区分已验证/待核验，并用线型、标签、节点形状共同编码，优于仅用颜色。
- 一些新控件已使用原生 button + `aria-expanded` / `aria-pressed`（候选展开 `1193`、过程记录 `1404`、问题选择 `1615`），可作为全局修复模板。
- reduced-motion 媒体查询存在（`200`）；全屏具有 Escape 退出监听（`2722`），这些是已有良好基础，不应因红队发现而忽略。

## 视觉美观与信息组织判断

以下为基于实际截图与源码的设计判断，属于专家评审，不是假装有统计依据的用户评分。

**优点**：单色与细线风格安静、没有多余装饰；图层切换、状态标签和 Inspector 卡片构成一致的视觉语言；浅/深主题中控件整体统一；在节点很少时，画布留白有利于定位关系。探索过程与本体结果分开，方向上有助于读者先找答案再追证据。

**不足**：图谱目前更像全局拓扑缩略图，缺少明确视觉焦点与阅读顺序。50节点截图中细线和极小标签占满同一水平带，关系、核心概念、边缘概念的视觉权重差别不足；用户首先看到“有很多知识”，难以快速回答“哪条最重要、哪条仍不确定”。全屏窄屏的图和详情比例失控，是布局完整性问题；普通375px工具条“适配/全屏”出现逐字换行，显得拥挤。大量11–12.5px辅助文字、小药丸和淡灰线条在宽屏截图中显精致，但容易形成“看上去轻、读起来费力”的体验。颜色主题统一不等于可读对比度已经合格。

**针对美观的具体方向**：图的首屏应有重点，而非把全部标签等比缩小；把结论摘要、风险/未决事项和证据入口置于稳定的阅读层级；图谱作为可探索视图，在概览时显示分组和关键节点，放大后逐层揭示标签。保持现有克制风格，优先修比例、密度和文字层级，再考虑装饰性润色。

## 优先改进顺序

1. 修复语义控件、键盘可达与焦点；修复窄屏抽屉挤压。
2. 为图谱设置可读默认视图、搜索/聚焦及文本替代；减弱自动 fitView 对用户操作的打断。
3. 对当前版本重新制作探索/本体截图，明确哪些证据来自真实 DSH、哪些来自夹具/模拟。
4. 增加英文/中文、浅色/深色、密集图、窄屏、键盘与屏幕阅读器任务检查。

本轮没有进行真实模型会话、生产会话浏览、完整英文页面操作、用户盲测或 WCAG 全量审计；这些不能标为通过。
