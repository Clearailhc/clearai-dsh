## 一、第一性原理

**起源。** 用 AI 做研究,最大的风险不是答不出来,而是答得太顺:已知、推测和编造用同一种口气说出来。人分不清哪句能信,下一次又从零开始。

- **认识论**回答「这句话凭什么能信」:一个结论可信,当且仅当它经受住了一次本可以让它失败的检验,并写清在什么情况下不成立。
- **本体论**回答「这些结论加起来是什么」:成立的结论沉淀成概念、关系和找到的具体东西,下一轮从已知出发。

**核心循环。** 这一轮所有取舍只用这一把尺子:

> 问题 → 判断(写明怎样算错)→ 一次可能失败的检验 → 证据 → 已确立的结论(带范围)→ 长进本体

**脚手架原则。** 模型的自我认知和长程能力会越来越强。ClearAI 只提供它自己做不到、也不该自己做的那部分——**事实边界**:什么算完成、谁的裁决有效、什么能写进知识。其余交给模型的判断,或交给宿主。

## 二、分工:宿主做什么,ClearAI 只做什么

### ClearAI 只做三件事

1. **认识论契约**:判断带推翻条件;判据先写后做;交付是唯一的完成动作,完成只看交付成立,结果是支持、推翻还是判不了都算完成;准入只判收不收;做的人不判自己(L3 以上派独立评估者);证据只增不删;结案前独立评估;升格为事实并带范围。
2. **本体**:词汇(概念、谓词)、实例、断言、冲突派生、图投影;已确立的结论跨会话留在工作区里,下一轮按概念取用。
3. **呈现**:「本体」格、「世界树」格、运行态卡。

## 三、目标层一步到位:怎么挂在原生 goal 上

- **目标本身用原生 goal。** 目标的文字、续跑轮数、暂停 / 阻塞 / 完成,全部由 `dsh-goal` 持有;人用原生界面与 `/goal` 管它。
- **ClearAI 只往当前 goal 上挂两样东西**:判据(怎样算完成)与判断(每条带推翻条件)。由一个工具 `Frame` 登记与修订;修订判据仍要一份独立裁决(防止中途挪球门)。
- **完成要过独立评估。** 结案工具 `Conclude`:派独立评估者逐条核对判据,判达成才把原生 goal 置为完成,并把达门槛的判断升格为事实。原生 `update_goal(complete)` 由 `ctx.tools.guard()` 拦下并指向 `Conclude`——这一条是机制,不是劝告。
- **人始终可以直接结束目标**(`/goal` 或原生界面)。那是人的决定,只结束目标,不把任何判断升格为事实。
- **要人时让原生 goal 停下。** 门开着(L4 待放行、计划连续被拦、事实出现反例待复核)时,ClearAI 把原生 goal 置为 blocked 并写明原因;人处理完,原生 resume。

## 六、代价与影响

1. **失去「恢复到某一版」**:宿主只能看每轮改了什么,不能恢复,宿主重启后也看不到之前的改动。安全改由宿主的权限预设与审批承担。(已接受)
2. **并行路线不再各有一份文件副本**:原生的子任务共用一个工作目录。两条路线要改同一批文件时会互相覆盖;产物路径不重叠只保证各自的产出不被覆盖。(已接受)
3. **状态形状变化**:旧会话的续跑窗口、世界线、侦察、账本事件不再被折成状态;旧日志仍可读,只是这些部分不再显示。`STATE_VERSION` 要升一版。
4. **文档大改**:循环哲学、验证闭环、领域本体、权威归属、真值表、已知缺口、README 都要按本方案重写;真值表 71 条机制会删掉一大半。

## 七、原型验证:三件事的结果

三件都在**真 DSH headless 宿主**(CLI 0.2.0-rc.2)里跑过:一个按剧本出牌的假模型走与真模型完全相同的工具管线、守卫与会话日志,不需要凭据。脚本在 `tools/spikes/`,`tools/spikes/run.sh <名字>` 可复现。

### 1. 原生 goal 的完成能否被可靠拦下 —— **能**

- 模型调 `update_goal(action=complete)` 被 `ctx.tools.guard()` 拒绝,goal 仍是 `active`(revision 1);ClearAI 的结案工具调服务 `ctx.goals.complete()` 后变为 `complete`(revision 2)。
- PTC 模式(`DSH_TOOLS_MODE=ptc`)里,`run_code` 程序内嵌套调 `tools.update_goal(complete)` 同样被拒,goal 仍是 `active`。
- 读源码确认:原生续跑驱动只会把 goal 置为阻塞,从不置为完成;`ralph`、`agent-team` 也不调 `goals.complete`。
- **仍能完成 goal 的只有人**:`/goal` 命令与原生界面的完成按钮。这是人的权力,保留;第三节据此补一句「人可以直接结束目标,那不算『已确立』」。

### 2. 人的决定能否不可伪造地落账 —— **能,而且不需要自建通道**

- 做法与原生 `exit_plan_mode` 相同:内核自己的工具在执行时直接调 `ctx.userQuestions.ask()`。问题与选项由内核写,答案在进程内交回内核。模型只能触发询问,碰不到答案。
- 伪造尝试都没进账:
  - 模型自己调 `ask_user_question` 问「撤回 F1?」,人也答了「撤回」,内核账仍为空;
  - 模型在正文里声称「用户已同意撤回 F1」,内核账也为空。
- 只有内核亲自问出的那条落账:`{fact: F1, decision: withdraw, by: human}`;人选「维持」时同样如实落为 `keep`。
- 没有人能回答时(headless、无界面),`ask()` 报 `NO_PROVIDER`,内核不替人决定:门保持开着,并让原生 goal 停下等人。
- 子代理不能问人(宿主拒绝),独立评估者本来也不该问人,不冲突。
- 进程重启时,正在等的那次询问会消失,但门的状态在内核里,下次再问,不丢决定。
- **结论**:第二节「问人」一行确定——自建人门路由、收件箱、动作白名单整套删掉,人门改为内核工具直接问人。

### 3. 原生 `present` 与准入的关系 —— **准入收下即自动交付**

- 准入核对产物存在且非空,空文件被拒收、不声明。
- 收下之后,内核自己往会话日志追加一条 `deliverables/presented`(与原生 `present` 写的是同一种事件、同一回合、同样的字段)。原生交付卡片按回合读它,模型不必再调一次 `present`。已读原生卡片的校验代码,它只核对字段形状,内核写的这条能通过。
- 模型自己调 `present` 交其他文件照常可用,内核也看得见(`tools/result`),不拦。
- **结论**:第二节「交付物」一行确定——计划步骤的产物经准入收下、在结案时一次声明为原生交付卡片;「产物」页签与它的宿主读面删掉。

### 由此拍板的两处(已确认)

1. **人门由开门的那次调用当场问。** 例如 L4 放行、计划连续被拦,都由 `AdvancePlan` 问;推翻证据碰到已升格的事实,由收到这条证据的那次交付或结案问。不新增工具,10 件不变。没人能答时,门开着,原生 goal 停下等人。
2. **交付卡片只在结案时出。** `Conclude` 通过后,把各步收下的产物一次声明为交付物;过程中的步骤产物不出卡片。

**真模型验收**:网络放行后,用 deepseek-flash 跑一场完整知识任务,确认删完之后主链(立约 → 计划 → 交付 → 独立评估 → 结案升格)不受影响。

### 第二阶段基线的发现(2026-10-02,已确认改法)

用模拟宿主让 Claude 扮演模型,跑了竞争路线、证伪、长链三个剧本(记录在 `docs/optimization/sim-runs/2026-10-02-p2-baseline/`)。三场判分都过,但竞争路线与证伪两场独立撞上同一处缺陷:**`AdvancePlan` 只在裁决为支持时推进步骤**,输的那条路线做完了、判据也满足了,却只能带因作废。

从第一性原理看,这把两种对象的生命周期绑在了一起:**步骤**是一个动作,它的状态回答「有没有按约做到」;**判断**是一条主张,它的状态由证据算。用结果合不合判断的意去定动作完没完成,是范畴错误,而且在机制上惩罚推翻、奖励把推翻改写成支持——与「本可以让它失败的检验」正面冲突。同一个 `verdict` 字段也被两种人读成两个意思:评估者用它说「交付成立」,自判的模型用它说「判断被推翻」。

已确认的改法(第三阶段落地):

1. **步骤推进只看交付成立。** 成立即推进,结果是支持、推翻还是判不了都算完成;不成立(产物缺、读数不真、与判据对不上)就退回,步骤留在 open。
2. **结果单独记成证据。** 判断的状态照旧由证据算,升格门槛不变;判不了是合法的零结果,判断保持原状、继续挂在卡上,要不要再设计更强的检验是下一步的决定——不靠「一直重做到有结论」。
3. **裁决拆成两项**:交付成立吗 / 对每条判断意味着什么。L0–L2 做的人自判,L3 以上两项都由独立评估者判,评估者的任务书写明「对照推翻条件读结果」。
4. **不检验判断的步骤不要求给结果。**
5. **一步可以检验多条判断**,每条各得一份证据:竞争路线里,比较那一步是关键检验,一份观测同时支持一条、推翻另一条。

### 第三阶段的改动清单(已确认,2026-10-02)

| 改什么 | 代码 | 用户看得见的变化 |
|---|---|---|
| 目标挂到原生 goal | `SetGoal` 改名 `Frame`:判据与判断挂在当前原生 goal 上;没有原生 goal 时由 `Frame` 建一个(目标那一句话就是它的 objective),修订时同步改 objective | 目标的文字、暂停、阻塞、完成都在原生 goal 上看与管;`/goal` 由原生接管 |
| 结案过独立评估 | `CloseGoal` 改名 `Conclude`:评估通过才调 `goals.complete()`,同时升格事实、把各步收下的产物一次声明为原生交付卡片(`deliverables/presented`);放弃时把原生 goal 置为阻塞并写明原因,由人决定结束 | 结案后对话里出现一张交付卡片;放弃时目标停在「阻塞」等人 |
| 守卫 | 已立约(`Frame` 过)的会话里,模型调原生 `update_goal(action=complete)` 被拒,指向 `Conclude`;人用 `/goal` 或界面结束目标不受影响,但不算任何判断已确立 | 无 |
| 删续跑窗口 | 续跑窗口账本(`continuation/set`)、布防 / 对齐 / 收兵 / 按住那一整套、`maxAutoTurns`;续跑由原生 goal 的驱动自己做 | 无(续跑照常,由原生驱动) |
| 删运行档 | `autonomy` 配置、两套澄清措辞只留一套、运行档事实与卡上那一行;连拦阈值只看 `blockedThreshold` | 卡上不再有「运行档」 |
| 删计划审阅与授权记号 | `RequestPlanReview`、审阅卡、`plan/confirmed` 与「未授权就按住续跑」;要先审计划,用原生 `/plan` | 立计划不再自动弹审阅卡 |
| 人门由开门的那次调用问 | `AdvancePlan`:L4 交付前问人放行(取代宿主审批瀑布)、同一步连拦到阈值时问人怎么办;收到推翻证据碰到已升格事实的那次交付或结案,问人撤回还是维持。都走 `ctx.userQuestions.ask()`,答案在进程内落账 | 这三处都弹原生提问卡,不再去面板收件箱点 |
| 没人能答时 | `ask()` 报 `NO_PROVIDER` 时门保持开着,原生 goal 置为阻塞并写明原因 | 目标停在「阻塞」,写着在等什么 |
| 人门路由收窄 | `/api/clearai/gate` 去掉撤回 / 维持事实两个动作;面板收件箱里「事实被推翻」「计划被拦」两类条目删掉。本体编辑那几个动作留到第六阶段随编辑抽屉一起删 | 面板不再有这两类待办 |
| 完成与结果分开 | `AdvancePlan`:交付成立即推进,结果是支持、推翻还是说不清都算完成;裁决拆两项(交付成立吗 / 每条判断的结果),评估者 schema 与任务书同步;不检验判断的步骤不要求给结果 | 推翻的那一步正常完成,不必作废 |
| 一步检验多条判断 | 步骤的 `tests.hypotheses`(数组,旧的单条 `tests.hypothesis` 照旧读);证据带上它针对的判断 | 比较那一步可以同时判竞争的两条 |
| 状态版本 | `STATE_VERSION` 升一版;旧日志里的续跑窗口、运行档、授权记号事件被安静跳过 | 旧会话照样打得开 |

**提示词**这一阶段只改到「名字与行为对得上」:`SetGoal`→`Frame`、`CloseGoal`→`Conclude`、删掉审阅卡与运行档的说法、补上完成与结果分开;整体改写成三段留到第五阶段。
