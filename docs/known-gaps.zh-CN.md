# 已知缺口

以下是这一版**诚实的边界**。每一条要么没做，要么只做到写明的深度。本文没列、别处也没演示过的，一律当作未验证。

**读法**：凡本仓库别处用未来式或理想式描述机制的段落，以本文与
[机制真值表](optimization/truth-table.zh-CN.md) 为准——真值表逐条标了 `已实现 / 部分实现 / 设计目标`，
并标出「文档说 A、代码是 B」的每一处。`current` 与 `design goal` 混着写，是这套文档过去最大的毛病。

## 还没实现

- **验证的八状态机。** [验证本体](verification-loop.zh-CN.md) 描述了验证对象的完整状态机。真正落地的只是内核实际执行的那一部分：命题、观测、评估、证据、事实，以及 L0–L4 五个等级。更完整的那套生命周期仍是设计目标。
- **普遍的 L4 人放行门。** L4 的**步骤/分支级**人放行已实现：交付必须有针对该步骤（或该世界线分支）的人放行记录，内核没有记录就拒收。覆盖每一次评估的全局闸门尚未实现。
- **计划授权是归属，不是闸门（这是已拍板的设计，不是待定项）。** 计划审阅卡**永远**会请人批准（`CreatePlan` 里没有自动确认分支，`confirmed_by` 的第三种来源 `'autonomy'` 已删除），审阅卡就是闸门本身——只有人批准才落 `by='user'` 的记号。但**未授权并不阻断显式交付**：未授权只让自动续跑 `hold`，`AdvancePlan` 照常执行并在同一条变更里补写 `confirmed_by='progress'`（行为即授权）。一句话：未经人批准的计划不会自动续跑；你显式推进时，第一次交付按事实记下归属。内核消息、运行态卡、提示词三处说的是同一句话。
- **`retracted`（已撤回）的生产者。** 本体里定义了这个状态，但目前没有任何代码路径会写它。
- **`self` 与 `scout` 之外的观测来源标注。** 类型里有别的来源，但还没有东西写它们。
- **机器评估者自动重跑。** 准入判出 `needs_audit` 时内核会派独立评估者，评估者是一个**真的子会话**；此外没有单独的后台重评循环。
- **真浏览器里的逐屏走查仍未做。** `/` 命令菜单（`/goal` `/plan` `/evidence` `/worldline` `/plan-review`）与挂回的原生工作方式（todo/subagent/workflow/ralph）已由组合测试与 headless e2e 验证，但浏览器里菜单弹出、命令渲染、面板与命令的一致性还没逐屏点过。

## 只验到写明的深度

- **事实行的跳转。** 「点一条已确认事实 → 跳到产生它的那一步」只在节点渲染层面验过，还没有在**真的升格过事实**的会话里用真浏览器点过。
- **计划审阅的措辞。** 人门措辞已在代码里改正并有测试覆盖，但改正后的文案还没在真浏览器里重看过。
- **装出来的客户端半在浏览器里。** 用 `dsh plugin add` 装出来的插件在浏览器里跑，在这次发布验收之前**从没验过**。这次验收抓到一个真缺陷：客户端 bundle 用旧包名注册自己，浏览器因此拒绝注册整个插件，所有面板一起静默消失。已修，并且这条检查已经进了发布验收。
- **本文档的英文与中文同步。** 两份文档同时维护；改动只落一边时无法自动发现。

## 结构性限制

- **灵魂映射是人工维护的。** [灵魂映射](soul-map.zh-CN.md) 把每条原则映到承载它的机制与测试。文字宪法与实现之间**没有机械等价检查**；这份表会漂移，只靠复查维持诚实。
- **有些原则仍然只是偏好。** 约束只写在提示词、没有机制承载时，映射表会如实注明，而不是暗示它被强制。
- **案例文档是示意，不是证据。** [`docs/cases/`](cases/) 写的是循环在三类问题上的行为。它不是基准测试套件，这个库也不随发布附带任何跑批记录。

## 待定项

- **英文界面与英文提示词（已部分修正，2026-09 对齐）。** 安装侧的 CLI（`doctor`、`install`、`seed`）打印的仍是中文，浏览器面板的文案也仍以中文为源（有英文表，但未在真浏览器里逐屏校对）——于是非中文用户拿到的仍可能是一套中文界面。
  **已经改了的那一半**：预设提示词**不再要求全程中文**，现在是「跟着用户当前语言走、一轮只说一种」（`preset/plugins/prompts.js` 的 language 小节）。所以"提示词把人锁死在中文"这条已经成立不了。
  仍然开着的设计决定只有一个：CLI 输出用哪种语言（面板那一侧复用 DSH 原生 locale 服务即可，机制已经在位）。

## 跑起来之前

- **pnpm 是前置条件，而且它是 DSH 的，不是本插件的。** `dsh plugin …` 转发给 pnpm，所以 `PATH` 上必须有一个可执行的 `pnpm`；没有它，CLI 会停在 `pnpm not found on PATH`，profile 也就完全管不了。直接装它（`npm install -g pnpm`，或用系统包管理器）。`corepack enable` 是那条诱人的近路，但它**不是安装**：它往 `PATH` 上放一个版本**转发器**，首次调用时才去下载某一版 pnpm。Node 24 自带的那份 corepack 0.34 靠找 `bin/pnpm.cjs` 来启动 pnpm，而 pnpm 从 11 起就不再提供这个文件（改成 `bin/pnpm.mjs`，再往后是包根目录的原生二进制），于是它可能下载一个自己启动不了的版本；它的 shim 还可能排在**本来就可用**的那份 pnpm 前面，把它遮住。
- **装插件靠的是 DSH CLI 本身，它随 npm 包 `@deepseek-ai/dsh` 发行。** 用 `npx` 起 harness **不会**把 `dsh` 放到你的 `PATH` 上——那一份住在 npx 缓存里，只对那一个进程有效。所以要么借它来装（`npx @deepseek-ai/dsh plugin --profile web add clearai-dsh`），要么用 `npm install -g @deepseek-ai/dsh` 把 CLI 装一次。
- **装完要重启 `dsh web`。** 宿主半与客户端半都缓存在运行中的进程里；只刷新浏览器不够，而在包被替换之后继续跑着的进程会端出一份坏掉的客户端 bundle。

## 运行期的两个坑

- **世界线的分支在账本里,不在你的文件夹里。** 工作区本身不是 git 仓库时,内核在
  `$DSH_HOME/storages/clearai/ledger/<slug>` 维护一个**旁路账本仓库**,把工作区当成它的工作树;
  分叉的分支与工作副本都住在那里。**删掉或清掉那个目录,会让还活着的分叉变成孤儿**:计划上分叉还开着,
  但它的分支与工作副本都没了。

  这在 2026-09-12 之前会**卡住整份计划**:分叉是按 git 分叉落账的,收敛时就会一直去合并一个已经不存在的分支。
  现在内核在**收敛那一刻**核对两件事:分支 ref 还能不能解析、工作副本目录还在不在;不在就不合并,
  **照样登记这次采纳**,如实记下"没有合并",并把"把赢家的产物落进声明位置"留给一次普通交付。
  计划不会再被一个机制上不可能收敛的对象卡死。
- **合并是"采纳"把赢家的文件落回来的方式。** 一条世界线就是一份独立的工作副本 + 自己的分支;
  采纳它意味着把它带回工作区。DSH 本身没有"给工作区开分支"这种原语,所以这一层是 ClearAI 的,
  架在宿主原生的子代理与会话日志之上。完全没有可用 git 上下文时,内核**不合并**:它登记这次采纳,
  把"把产物落进声明位置"留给一次普通交付。
