# 已知缺口

以下是这一版**诚实的边界**。每一条要么没做，要么只做到写明的深度。本文没列、别处也没演示过的，一律当作未验证。

**读法**：凡本仓库别处用未来式或理想式描述机制的段落，以本文与
[机制真值表](optimization/truth-table.zh-CN.md) 为准——真值表逐条标了 `已实现 / 部分实现 / 设计目标`，
并标出「文档说 A、代码是 B」的每一处。`current` 与 `design goal` 混着写，是这套文档过去最大的毛病。

## 还没实现

- **验证的八状态机。** [验证本体](verification-loop.zh-CN.md) 描述了验证对象的完整状态机。真正落地的只是内核实际执行的那一部分：命题、观测、评估、证据、事实，以及 L0–L4 五个等级。更完整的那套生命周期仍是设计目标。
- **普遍的 L4 人放行门。** L4 的**步骤/分支级**人放行已实现：交付必须有针对该步骤（或该世界线分支）的人放行记录，内核没有记录就拒收。覆盖每一次评估的全局闸门尚未实现。
- **计划授权是归属，不是闸门（这是已拍板的设计，不是待定项）。** 计划审阅卡**永远**会请人批准（`CreatePlan` 里没有自动确认分支，`confirmed_by` 的第三种来源 `'autonomy'` 已删除），审阅卡就是闸门本身——只有人批准才落 `by='user'` 的记号。但**未授权并不阻断显式交付**：未授权只让自动续跑 `hold`，`AdvancePlan` 照常执行并在同一条变更里补写 `confirmed_by='progress'`（行为即授权）。一句话：未经人批准的计划不会自动续跑；你显式推进时，第一次交付按事实记下归属。内核消息、运行态卡、提示词三处说的是同一句话。
- **人上传 / 文件投递 / 回调 / 拉取这四种外部来源。** 等级表（L4）列了它们，但**观测对象今天只有 `self` 与 `scout` 两个来源**——类型只声明真有生产者的取值（多一个是类型里的假话）。等这四种入口真的接上，再回来把取值加进声明。
- **~~面板「本体」页签与图编辑（阶段 D–E）~~（已于 0.2.0 落地，本条是过时说法，留痕）。**
  本体图 / 实体图、按概念筛选、断言芯片就地展开词条卡、冲突行与内联标记、折叠的词汇维护区，
  以及经人门通道的图编辑（登记 / 修订 / 废止，复用同一份判据）都已经有界面。
  见[开发计划](optimization/domain-ontology-plan.zh-CN.md)的阶段 D–E。
- **领域本体没有跨项目的词汇复用。** 词条是**项目级**的（随工作区账本走）：
  换一个项目就要重新登记；「我的词汇库」这种用户级复用是一件事，本版不做。
- **知识模式与知识门只有单元测试的保证，还没有一场真跑。** 分诊的判据是结构的
  （目标还开着且带着登记过的命题），知识门在结案、派评估者之前拦下没有形态的命题
  （`requireTypedPromotion`，内核缺省关、preset 里开）。两者都由测试钉住行为，
  但**没有在真实长跑里看过它们对模型行为的实际影响**——特别是「模型会不会为了让门放行而编一个词」。
  另外知识门在设计上是**会给正在跑的会话带来一次拒绝**的（它们按老纪律走到了结案），
  这次拒绝给的是两条可执行的路，不是一句禁令；这一点的措辞也只见于测试。
- **图带的交互（拖动、缩放、悬停、键盘）只在测试里验过结构，没在真浏览器里点过。**
  测试能钉住「按连接度取前 N、只画两端都在场上的边、截断说明的措辞」，
  钉不住 Pointer Events 的真实行为、以光标为中心的缩放手感、以及拖动手势与点击的分离。
- **旧账本里没有断言的已升格事实，补不上断言。** 它们继续以「未结构化」在架上，
  **不算欠账**（知识模式的缺口读数刻意把它们排除：算成欠账就是一条永远还不掉的抱怨）。
- **机器评估者自动重跑。** 准入判出 `needs_audit` 时内核会派独立评估者，评估者是一个**真的子会话**；此外没有单独的后台重评循环。
- **真浏览器走查已做一轮（深度写死在这里）。** 干净安装 + 真 Chrome + deepseek-flash 的一整场：预设可切换、原生审阅卡弹出、人点 Approve 后授权记号以 `by='user'` 落账、十三拍主链走完（含独立评估者子会话与两条事实升格）、`/goal` 在原生菜单渲染、Deliverables/Facts/Worldlines/Skills·Memory 四个面板出图（截图在 `docs/shots/browser-e2e-*.png`）。**没验的**：长会话下的面板交互细节（出处跳转、命题展开）、`/evidence` `/worldline` `/plan-review` 三个命令的浏览器渲染、英文界面。另外 **README 的面板截图需要重拍**：本体格（图带/货架/芯片/冲突）是新面，旧的四张截图没有它；旧的「事实」格文案也变了。

- **子 run 的结论送达与结算依赖内核自己,不依赖运行时的尽力投递（已定稿的设计,不是待定项）。** 四类子 run
  （侦察 / 世界线执行者 / 评估者 / 横评仲裁）统一走 `subagents.start()` 的一次性句柄：账本只认本进程攥着的
  `run.result`，结论正文由**收集那一刻的工具返回**交给模型。原生结算通知只当锦上添花——它是 best-effort，
  实测在活进程里并不总能被内核通过投影或本会话日志看到，因此**不作承重结构**。
- **进程重启后能不能收回子 run 的结论，目前只有单元测试的保证。** 子会话日志回收
  （`recoverFromChildSession`）是现行代码里的慢路径，但在部署形态里没有读出过结论（实测那次执行者走的是句柄）。
  也就是说：**重启恢复这条能力没有真跑证据**。
- **一次性形态没有「下一回合」。** 子 run 若在父会话最后一个收集点之后才落定，账本收不到它；
  长测不变量会把它如实标成「悬空」，不会假装收过。常驻形态有下一回合，不受此限。
  **回合收尾记的是工作区，不是「谁还在飞」**：宿主的 `agent/turn-stopping`（回合将停时串行 await）上，
  内核把这一回合的写入落成一笔工作区账本快照（`git/snapshot`）——它**不判在飞、不写裁决、不叫醒任何人**。
  **回合以错误结束**（提供方连接错误、重试耗尽——真跑里最常见的那种"半路死"）走另一条路：
  宿主在那一档**不派** `agent/turn-stopping`，所以内核同时盯着 `agent/error`，快照照样落。
  「还有谁在飞」由**下一回合的运行态卡去问宿主**（`subagents.listChildren`），
  不从收尾这一刻的观察里推断——那是推论，不是事实。
  仍然留着的是**硬杀**（SIGKILL／超时强杀）：那一拍也来不及跑，账上只剩派发事实。
- **目标轴的裁决仍可能"悬空"：进程被硬杀时，一条 `audit/dispatched` 既没有 `audit/settled`、也没有别的收尾记录。**
  已证实的那一半已经修掉：`runEvaluator` 三条 `unknown` 出口（评估者失败 / 没正常结束 /
  **评估卡落盘失败**）不再只留派发事实，三条路都照落 `audit/settled{verdict:'unknown'}`——结局不好也是结局；
  `sweepEndedAudits` 也会先**从子会话日志取回**裁决（与侦察同一条路，`recoverVerdictFromChildSession`），
  取不回才如实落 unknown，`ended_uncollected` 与 `lost` 分开写，结算文案不再给建议
  （「重新交付会派一个新的评估者」那句删了——要不要重试是计划层的决定，不是账本该说的话）。
  仍然留着的是**硬杀／进程消失**：那一拍没有执行者，账上只剩派发事实。
- **结算现在有宿主事件这一路（`subagent/end`），但它同样只保证在活进程里。** 该事件由持有
  `run.result` 的 service 在同一个 promise 落定那一刻发出（成功与失败都发），所以 handle 不在也收得到；
  进程已经死了就什么都没有——那种情况仍靠子会话日志回收。
- **常驻形态（web）在本轮重构后尚未重新验证。** 真浏览器那一场跑在生命周期统一之前；
  本轮改的是结算与送达路径，浏览器侧的续跑窗口与面板表现需要重跑一次验收。
- **长测的重型现场只在本地。** 工作区现场与会话日志原件落在 `~/.dsh/e2e-archive/`（不入库，避免仓库膨胀），
  入库的是轨迹解码件、结构化结果与出处。换台机器克隆仓库，拿不到原始会话日志。

## 只验到写明的深度

- **领域词汇的校验只到「形状」为止。** 值形态、主词域、值域、`is_a` 成环、同一事实自冲突都在落账前判；
  **不判**量纲换算与数值容差，**不解析**公式语义，**不查** `code` 形态指向的文件在不在
  （文件系统是另一侧的事，且那一步会让折法沾上 I/O）。
- **冲突只暴露，不裁决。** 两条未撤回的已确认事实落在同一单值谓词、同一主体、不同客体时，投影给出一对冲突读数：
  它**不撤回任何一侧**、不判断哪条为真、也不进闸门。要处置就走既有的人门（`fact/reviewed`：撤回或维持）。
- **实体图里的实例不注册、也不去重。** 实例节点从断言里投影出来，同名即同节点；
  实体消解（同一事物的两种叫法）不做。
- **旧事实补不上断言。** 断言只在升格那一刻落地——0.2.0 之前升格的事实（以及任何没写断言的事实）
  永远显示为「未结构化」，不会被回溯改写。

- **账本的覆盖面是「每回合一次」,不是「每次写入一次」。** 本会话写过东西的每一道回合边界都落一次
  工作区快照,所以探索产出可查、可恢复;它**不提供的是归属**——内核看不见 `bash` 产出了什么,
  所以工作区 git 历史里永远不会说「哪一笔写入属于哪一次工具调用」。设计里的「每次写入都带
  turn/tool 归属」这一条,是刻意不声称的。
- **事实行的跳转。** 「点一条已确认事实 → 跳到产生它的那一步」只在节点渲染层面验过，还没有在**真的升格过事实**的会话里用真浏览器点过。
- **计划审阅的措辞。** 人门措辞已在代码里改正并有测试覆盖，但改正后的文案还没在真浏览器里重看过。
- **装出来的客户端半在浏览器里。** 用 `dsh plugin add` 装出来的插件在浏览器里跑，在这次发布验收之前**从没验过**。这次验收抓到一个真缺陷：客户端 bundle 用旧包名注册自己，浏览器因此拒绝注册整个插件，所有面板一起静默消失。已修，并且这条检查已经进了发布验收。
- **本文档的英文与中文同步。** 两份文档同时维护；改动只落一边时无法自动发现。

## 结构性限制

- **灵魂映射是人工维护的。** [灵魂映射](soul-map.zh-CN.md) 把每条原则映到承载它的机制与测试。文字宪法与实现之间**没有机械等价检查**；这份表会漂移，只靠复查维持诚实。
- **有些原则仍然只是偏好。** 约束只写在提示词、没有机制承载时，映射表会如实注明，而不是暗示它被强制。
- **案例文档是示意，不是证据。** [`docs/cases/`](cases/) 写的是循环在三类问题上的行为。它不是基准测试套件，这个库也不随发布附带任何跑批记录。

## 待定项

- **英文界面与英文提示词（已部分修正，2026-09 对齐）。** 安装侧的 CLI（`doctor`、`install`、`seed`）打印的仍是中文，浏览器面板的文案也仍以中文为源（有英文表，但未在真浏览器里逐屏校对）——于是非中文用户拿到的仍可能是一套中文界面。
  **已经改了的那一半**：预设提示词**不再要求全程中文**，现在是「跟着用户当前语言走、一轮只说一种」（`preset/plugins/prompts.js` 的 language 小节）。所以"提示词把人锁死在中文"这条已经成立不了。
  仍然开着的设计决定只有一个：CLI 输出用哪种语言（面板那一侧复用 DSH 原生 locale 服务即可，机制已经在位）。

## 跑起来之前

- **pnpm 是前置条件，而且它是 DSH 的，不是本插件的。** `dsh plugin …` 转发给 pnpm，所以 `PATH` 上必须有一个可执行的 `pnpm`；没有它，CLI 会停在 `pnpm not found on PATH`，profile 也就完全管不了。直接装它（`npm install -g pnpm`，或用系统包管理器）。`corepack enable` 是那条诱人的近路，但它**不是安装**：它往 `PATH` 上放一个版本**转发器**，首次调用时才去下载某一版 pnpm。Node 24 自带的那份 corepack 0.34 靠找 `bin/pnpm.cjs` 来启动 pnpm，而 pnpm 从 11 起就不再提供这个文件（改成 `bin/pnpm.mjs`，再往后是包根目录的原生二进制），于是它可能下载一个自己启动不了的版本；它的 shim 还可能排在**本来就可用**的那份 pnpm 前面，把它遮住。
- **装插件靠的是 DSH CLI 本身，它随 npm 包 `@deepseek-ai/dsh` 发行。** 用 `npx` 起 harness **不会**把 `dsh` 放到你的 `PATH` 上——那一份住在 npx 缓存里，只对那一个进程有效。所以要么借它来装（`npx @deepseek-ai/dsh plugin --profile web add clearai-dsh`），要么用 `npm install -g @deepseek-ai/dsh` 把 CLI 装一次。
- **装完要重启 `dsh web`。** 宿主半与客户端半都缓存在运行中的进程里；只刷新浏览器不够，而在包被替换之后继续跑着的进程会端出一份坏掉的客户端 bundle。

## 运行期的两个坑

- **世界线的分支在账本里,不在你的文件夹里。** 工作区本身不是 git 仓库时,内核在
  `$DSH_HOME/storages/clearai/ledger/<slug>` 维护一个**旁路账本仓库**,把工作区当成它的工作树;
  分叉的分支与工作副本都住在那里。**删掉或清掉那个目录,会让还活着的分叉变成孤儿**:计划上分叉还开着,
  但它的分支与工作副本都没了。

  这在 2026-09-12 之前会**卡住整份计划**:分叉是按 git 分叉落账的,收敛时就会一直去合并一个已经不存在的分支。
  现在内核在**收敛那一刻**核对两件事:分支 ref 还能不能解析、工作副本目录还在不在;不在就不合并,
  **照样登记这次采纳**,如实记下"没有合并",并把"把赢家的产物落进声明位置"留给一次普通交付。
  计划不会再被一个机制上不可能收敛的对象卡死。
- **合并是"采纳"把赢家的文件落回来的方式。** 一条世界线就是一份独立的工作副本 + 自己的分支;
  采纳它意味着把它带回工作区。DSH 本身没有"给工作区开分支"这种原语,所以这一层是 ClearAI 的,
  架在宿主原生的子代理与会话日志之上。完全没有可用 git 上下文时,内核**不合并**:它登记这次采纳,
  把"把产物落进声明位置"留给一次普通交付。
