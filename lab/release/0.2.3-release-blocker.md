# 0.2.3 发布阻塞诊断:宿主预设注册机制换代

- 诊断时间:2026-09-28 10:46 (+08:00)
- 触发场景:tag `v0.2.3` → release workflow run [36370225052](https://github.com/Clearailhc/clearai-dsh/actions/runs/36370225052)
- 结论:**不是 0.2.3 的内容坏了,是宿主换代了**。npm 上**没有任何副作用**(publish 及其后的回查、建 Release 全部 skipped)。

## 1. 现象

release workflow 在第 11 步 `Clean install (mechanical half)`(`node tools/verify-clean-install.mjs`)失败,13 通过 / 2 失败:

```
✗ ④ 名册 root 指向包内 presets/,且 trust 是 system
✗ ④′ 没有把发行版 root 挤掉(includeShippedRoot 仍为 true)
```

前面 10 步全绿,**包括** `Suites`(全部套件)、`Build and self-check`、`Tag must match the manifest`。失败的两条都只关于**一件事**:agent 预设的注册方式。

注意 ④ 失败时**没有** detail 文本。断言实现是:

```js
const rosterLine = composed.slice(composed.indexOf('includeShippedRoot'), composed.indexOf('includeShippedRoot') + 600)
check('④ …', /node_modules\/clearai-dsh\/presets\//.test(rosterLine) && /trust:\s*system/.test(rosterLine), rosterLine.replace(/\s+/g, ' ').slice(0, 120))
```

`indexOf` 返回 -1 时 `slice(-1, 599)` 得到空串,detail 即为空——**这正是「组合里根本没有 `includeShippedRoot` 这个键」的指纹**,而不是「它的值不对」。

## 2. 证据链

### 2.1 同一份包,09-23 绿、今天红,变的只有宿主

- `e362acc` 上的 CI run [35857872272](https://github.com/Clearailhc/clearai-dsh/actions/runs/35857872272)(2026-09-23)结论 **success**,它同样跑 `verify-clean-install.mjs`。
- `main` 自 `e362acc` 起没有新提交,包内容一字未变。
- workflow 用 `npm install @deepseek-ai/dsh`(无版本 = `latest`)。
- 今天实测:registry 上 `@deepseek-ai/dsh` 的 `dist-tags.latest = 0.1.7-rc.2`(2026-09-24 发布)。而 `0.1.7-rc.1` 发布于 2026-09-23T13:44Z —— 恰在 09-23 那次绿 run(12:00Z)**之后**。

### 2.2 宿主把「名册扫目录」换成了「组合里的声明行」

**旧机制(≤ 0.1.6-alpha.2)**:`@deepseek-ai/dsh-web-app/cordis.patch.yml`

```yaml
- insert:
    - id: agent-presets
      name: '@deepseek-ai/dsh-agent-presets'
      config:
        default: standard
```

配套注释写明这套设计:「shipped presets 打包在 `dsh-agent-presets` 里,作为只读 `system` root 前置(`includeShippedRoot`);`$DSH_HOME/.agent-presets` 是用户自己写预设的地方(`includeUserRoot`)」。**预设 = 一个目录,名册去扫它,root 带 trust。**

**新机制(0.1.7-alpha.2 / 0.1.7-rc.2)**:web-app 的 `cordis.patch.yml` 里已**没有** `agent-presets` 行,取而代之:

```yaml
# The preset selection registry. The shipped preset declarations follow as
# separate patch files under `presets/`, listed after this file in
# `package.json` `dsh.bundle.patch`.
- insert:
    - id: agent-preset-registry
      name: '@deepseek-ai/dsh-agent-preset-registry'
      config:
        default: standard
```

每个预设变成**一条独立的组合行**,各自一个补丁文件:

```yaml
# dsh-web-app/presets/cordis.patch.yml
- insert:
    - id: preset-cordis
      name: '@deepseek-ai/dsh-agent-preset'
      config:
        id: cordis
        order: 4
        plugins:
          - id: persona
            name: '@deepseek-ai/dsh-persona'
          - id: tool-fs
            name: '@deepseek-ai/dsh-tool-fs'
          # …整份预设的插件行都在这里
```

包用**数组**声明这些文件:

```json
"dsh": { "bundle": { "patch": ["./cordis.patch.yml", "./presets/standard.patch.yml",
                               "./presets/ptc.patch.yml", "./presets/minimal.patch.yml",
                               "./presets/cordis.patch.yml"] } }
```

新版 registry 插件的 schema(`dsh-agent-preset-registry/lib/types/index.d.ts`)只剩两个键:

```
default: z<string>
selectedDefault: z<string>
```

**`includeShippedRoot` / `includeUserRoot` / `roots` / `trust` 全部消失**——不再有目录扫描,也就没有「谁的目录更可信」这件事了。旧包 `@deepseek-ai/dsh-agent-presets`(复数)最新停在 `0.1.5-rc.3`,新宿主依赖里换成 `@deepseek-ai/dsh-agent-preset`(单数)。

### 2.3 机制切换的版本边界(实测)

| 宿主 | web-app 补丁里的名册行 | `dsh.bundle.patch` 形态 |
|---|---|---|
| 0.1.5-rc.3 | `id: agent-presets` | 单文件 |
| 0.1.6-alpha.2 | `id: agent-presets` | 单文件 |
| 0.1.7-alpha.2 | 无 `agent-presets`(已换代) | 数组 |
| 0.1.7-rc.2 | `id: agent-preset-registry` | 数组 |

即:**0.1.7-alpha.1 起换代**。`0.1.5-rc.3` 虽然后发(09-22),但仍是旧机制。

### 2.4 我们的包因此坏在哪一步

`pack/cordis.patch.yml` 里那段:

```yaml
- id: agent-presets
  config:
    default: standard
    includeShippedRoot: true
    includeUserRoot: true
    roots:
      - path: !!js "…new URL('node_modules/clearai-dsh/presets/', baseUrl)…"
        trust: system
```

它是一条**按 id 覆盖既有行 config** 的补丁。新宿主里 `agent-presets` 这个 id **不存在了**,于是这条补丁没有落点——而 profile 照样起得来(另一条 `- insert: [id: clearai-host, name: 'clearai-dsh']` 仍然生效),所以故障**只落在预设注册这一面**:

- ✅ 宿主半装上了(断言 ③/③′ 通过)
- ✅ 包内预设文件仍在发行物里(断言 ⑤ 通过)
- ✅ 没有本机路径泄漏(断言 ⑥ 通过)
- ❌ 名册不再指向我们的 `presets/` → **ClearAI 预设不进模式选择器**

## 3. 影响面

在 ≥ 0.1.7-alpha.1 的宿主上安装 clearai-dsh 的用户:**包能装、宿主行能起,但模式选择器里看不到 ClearAI**——预设是产品的入口,这等于功能不可用。

这不是 0.2.3 引入的缺陷:0.2.3 的包内容与 0.2.2 一致(`package.json` 版本号 + 中英 README,`e362acc` 那三个提交),它是宿主升级**砸到所有旧版 clearai-dsh 上**的兼容性断裂——0.2.2 及以前同样中招。

## 4. 三条路线

### 路线 1(推荐):先适配,以 0.3.0 发布

把预设从「root 目录」迁到「声明行」:

1. 新增 `pack/presets/clearai.patch.yml`,形态为新版声明行:`- id: preset-clearai, name: '@deepseek-ai/dsh-agent-preset', config: {id, name, description, order, plugins: […把 preset/agent.cordis.yml 的插件行搬进来…]}`。
2. `package.json` 的 `dsh.bundle.patch` 改成数组。
3. `tools/verify-clean-install.mjs` 的 ④/④′ 改成按宿主版本分档的断言(旧宿主验 root,新宿主验 registry 行 + `preset-clearai` 行 + 预设条目可列出)。
4. 版本号 → `0.3.0`,CHANGELOG 写明这是宿主机制的破坏性适配;0.2.3 那三条文档改动并入。
5. **待调研**:能否单包同时兼容两代宿主(旧宿主没有 `@deepseek-ai/dsh-agent-preset` 插件,新宿主没有 `dsh-agent-presets`,很可能做不到——需要一轮探针确认)。

### 路线 2:照发 0.2.3,把断裂记为已知缺陷

把 release workflow 的干净安装验收 pin 到兼容宿主(如 `0.1.6-alpha.2`),0.2.3 照发,同时在 CHANGELOG / Release 说明里写明「≥0.1.7 宿主上预设不可见,适配进行中」。

- 好处:今天就能发,版本号保持用户的预期。
- 代价:门禁变成「拿旧宿主的绿」证明新宿主可用;真实用户在新宿主上装到的仍是坏的。**这属于为了让门变绿而改门**,我不推荐,但如果你要先发布、适配另开,这是唯一诚实的实现方式。

### 路线 3:先只做兼容性调研,不动版本

派一轮只读侦察把适配全貌摸清(新版声明行的完整字段、`template/` 与 `skills/` 在新机制下归谁消费、两代兼容是否可能、`seed` 子命令是否要跟着改),再决定发 0.2.3 还是直接做 0.3.0。

## 5. 已排除的可能

- **不是 npm 发布身份的问题**:OIDC 配置在 0.2.2 上验证过,而且本次根本没走到 publish 那一步。
- **不是我们的包构建坏了**:`Suites`、`Build and self-check` 全绿,发行物结构断言 ⑤/⑥ 通过。
- **不是 tag/版本不一致**:`Tag must match the manifest` 通过。
- **不是网络或 credentials 缺失导致的环境性抖动**:失败是两条确定性的结构断言,不是超时或 4xx。
