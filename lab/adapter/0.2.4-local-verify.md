# 0.2.4 本地验证:ClearAI 预设在新宿主上真的可用

- 验证时间:2026-09-28
- 宿主:`@deepseek-ai/dsh@0.1.7-rc.2`(新机制),装在 `/tmp/dsh-cli-017`
- 方式:空 `DSH_HOME` + 真 pnpm + 真 `dsh plugin add` + **运行态名册读取** + 界面人工确认

## 一、结论

两条都做到了:

1. **组合层面**:干净安装后,`preset-clearai` 声明行与内置四个预设**并列**出现在 `dsh --profile web --dump-config` 输出里。
2. **可用层面**:**`agentPresets.list()` 返回的 clearai 条目没有 `broken` 字段**,并且在真实界面的预设选择器里**肉眼可见**。

第 2 条不是锦上添花,它是这次适配里**最容易漏掉的一环**——第一轮验证时组合层面完全正常,而实际上预设是坏的(见第三节)。

## 二、判据①:组合层面(dump-config)

```
$ DSH_HOME=/tmp/verify-home-024c dsh --profile web --dump-config | grep -n "id: preset-"
604:- id: agent-preset-registry
608:- id: preset-standard
790:- id: preset-ptc
978:- id: preset-minimal
1058:- id: preset-cordis
1250:- id: preset-clearai
```

`preset-clearai` 那一段的原文:

```yaml
- id: preset-clearai
  name: '@deepseek-ai/dsh-agent-preset'
  config:
    id: clearai
    name: ClearAI
    description: 利用认识论循环构建可信本体。Build a trustworthy ontology through the epistemic loop.
    order: 10
    plugins:
      - id: persona
        name: '@deepseek-ai/dsh-persona'
        config:
          prefix: >-
            你是 ClearAI 的主人格,运行在 DeepSeek Harness 上。
```

安装本身也正常:profile 的 `dependencies` 里有 `clearai-dsh`,`bundles` 是 `[dsh-base, dsh-web-app, clearai-dsh]`,`dsh plugin add` 退出码 0。

## 三、判据②:运行态名册 —— 三轮读数,前两轮都是坏的

`dsh --dump-config` 是**静态**的:它只说组合里有没有那条声明行。要知道预设**能不能用**,得读运行态的 registry。为此写了 `lab/scripts/read_preset_roster.mjs`——用宿主自己的 `profile-boot` 接口 boot 一个 profile,然后打印 `ctx.agentPresets.list()` 的原始结果。

### 第一轮:注册成功,但带着三条 broken

```json
{ "id": "clearai", "name": "ClearAI", "order": 10,
  "broken": "clearai-kernel (./plugins/clearai-kernel.js): never started
             clearai-commands (./plugins/commands.js): never started
             workflow-worker-thread (@deepseek-ai/dsh-workflow-worker-thread): never started" }
```

三类问题,两处根因:

- **相对路径不成立**:旧机制里 `./plugins/clearai-kernel.js` 相对 `agent.cordis.yml` 所在目录解析;换成声明行之后基准变了,两条本地插件因此从未启动。
- **引用了已下线的包**:`@deepseek-ai/dsh-workflow-worker-thread` 在旧宿主(0.1.5-rc.1)里存在,**新宿主里已经没有这个包**——宿主把 workflow 引擎换成了 `@deepseek-ai/dsh-workflow-ptc`。

**这正是界面里看不到 ClearAI 的原因**(用户第一次确认时即答「没看到」)。

### 修复(三处)

1. 两条本地插件改用**包内子路径**:`clearai-dsh/presets/clearai/plugins/clearai-kernel.js`,并在 `package.json` 的 `exports` 里加 `"./presets/*": "./presets/*"` 放行——从 profile 的 `node_modules` 解析,与宿主解析其它插件名同一条路。
   (顺带实测:声明行 `plugins[].name` **不接受 `!!js`**,写了会报 `row 1 names no plugin`;它只能是可解析的字符串。)
2. 删掉 `workflow-worker-thread` 那条已下线的行。
3. 在同一 group 内补上 `workflow-ptc`(`@deepseek-ai/dsh-workflow-ptc`,与官方 standard 预设同形,且必须与 `tool-workflow` / `tool-ralph` 同处那个 `isolate: { workflowEngine: true }` 的 realm)。

### 第二轮:两条相对路径的 broken 消失,但 workflow 相关仍有

```json
"broken": "tool-workflow (@deepseek-ai/dsh-tool-workflow): waiting for workflowEngine
           tool-ralph (@deepseek-ai/dsh-tool-ralph): waiting for workflowEngine"
```

`waiting for workflowEngine` 直接指明了缺的是服务提供者——补上第 3 处修复。

### 第三轮:干净

```json
{ "id": "clearai",
  "name": "ClearAI",
  "description": "利用认识论循环构建可信本体。Build a trustworthy ontology through the epistemic loop.",
  "order": 10 }
```

**没有 `broken` 字段。** 与内置四个并列:

```
条目:standard, ptc, minimal, cordis, clearai
含 clearai:true
```

### 界面确认(人工)

用一个由 0.1.7-rc.2 + 修复后的包起的一次性实例(`--port 3198`,独立于用户正在使用的 GUI),请用户在预设/模式选择器里查看:

- 修复前(同一手法起的实例,端口 3199):用户答 **「没看到」**——与名册里的 broken 一致。
- 修复后:**用户答「能看到 ClearAI 了」**。

## 四、这一步抓到了什么

**「组合里有」不等于「能用」。** 第一轮里,`dump-config` 干净、`dsh plugin add` 成功、profile 能正常启动——所有静态信号都是绿的,而预设实际是坏的(三个子插件全部未启动),界面上根本不出现。这正是 0.2.3 那次事故的同一形状:**门绿了,东西是坏的**。

要抓住它,需要的是**运行态**证据,而运行态在 CI 里拿不到(preset 的子插件只在会话选用时挂载,而 CI 没有模型凭据)。所以:

- 本地:**本文件**——名册读数 + 界面确认;
- CI:结构断言(见 `tools/verify-clean-install.mjs` 的改造),它证明「声明行正确、依赖可解析」,不冒名顶替「可用性」;
- 两者的分工写进发布报告。
