## 一、决定的来源与理由

**用户选择:删除远端 `v0.2.3`。** 理由:GitHub 上不留「有 tag、但没有 Release、npm 上也没有对应版本」的孤儿标记。

这个 tag 是 2026-09-28 上午这次发布尝试留下的:它被推送后触发了 release workflow,而流水线在「干净安装」那道门被拦下(宿主换代导致的预设注册断裂),publish、registry 回查、建 Release 三步全部 skipped。于是它的处境是:

- 指向 `e362acc`(0.2.3 内容写就的那个提交);
- npm 上**没有** `0.2.3`(从未发布,registry 未受任何影响);
- GitHub 上**没有**对应的 Release;
- 它的内容(版本号 + 中英 README)已并入 `0.2.4` 发布。

## 四、一个必须指出的遗留:本地 tag 仍在

本次只删了**远端**那一个(用户的指定范围)。本地 `git tag -l 'v0.2.*'` 仍列出 `v0.2.3`,于是:

**风险——`git push --tags` 会把它推回远端**,孤儿标记会原样复活。任何一次「把所有 tag 推上去」的操作都会触发。

两个选择,我没有擅自扩大范围去做:

```bash
git tag -d v0.2.3        # 一并清掉本地那一个,两边一致
```

或者保留它(它有本地价值:它标记着 0.2.3 那段内容写就的提交 `e362acc`,而 `v0.2.4` 的发布提交是它的后代,历史链没断)。

## 五、记账

`v0.2.3` 未发布这件事不是靠这个 tag 记的,而是写在 **CHANGELOG** 里(唯一账本):

```markdown
## [0.2.3] — 2026-09-23(未发布)

> 本版**从未发布到 npm**。它是纯文档版本(版本号 + 中英 README),在发布流水线上被宿主换代造成的断裂拦下——原样发出去的话,用户在新宿主上装到的包不进预设选择器。改动已并入 [0.2.4]。
```

所以即便远端 tag 不存在了,「0.2.3 是什么、为什么没发」仍然查得到;而那次失败的技术细节完整留在 `lab/release/0.2.3-release-blocker.md` 与 `products/reports/release-0.2.3.md`。
