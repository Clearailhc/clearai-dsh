# 0.2.4 适配设计:预设从「root 目录」迁到「声明行」

- 定稿:2026-09-28
- 背景与证据:`lab/release/0.2.3-release-blocker.md`
- 本设计的每条结论都由 `lab/scripts/probe_preset_mechanism.sh`、`lab/scripts/probe_preset_baseurl.sh`、`lab/scripts/probe_preset_baseurl2.sh` 三个探针在真实宿主上实测得出(0.1.7-rc.2 与 0.1.5-rc.1 两代并存对照)。

## 一、四个待定问题的结论

### Q1 声明行文件放哪、长什么样

**放 `presets/clearai/clearai.patch.yml`(发行物内路径),源由构建期生成。**

```yaml
- insert:
    - id: preset-clearai
      name: '@deepseek-ai/dsh-agent-preset'
      config:
        id: clearai
        name: ClearAI
        description: |-
          利用认识论循环构建可信本体。Build a trustworthy ontology through the epistemic loop.
        order: 10
        plugins:
          # ↓ 以下是 preset/agent.cordis.yml 的全部行,整体缩进 6 格搬进来
          - id: persona
            name: '@deepseek-ai/dsh-persona'
            config:
              prefix: |-
                …
```

**为什么放在 `presets/clearai/` 里而不是 `pack/` 下:**声明行里的 `plugins` 含两类**相对基准**的写法,而它们的基准是声明行所在补丁文件的目录:

| 写法 | 出现在 | 基准 = patch 文件目录 ⇒ 解析结果 |
|---|---|---|
| `name: './plugins/clearai-kernel.js'` | `agent.cordis.yml` 第 135/220 行 | `presets/clearai/plugins/clearai-kernel.js` ✅ 与旧机制**逐字相同** |
| `!!js "…new URL('skills/', baseUrl)"` | `agent.cordis.yml` 第 83 行 | `presets/clearai/skills/` ✅ 与旧机制**逐字相同** |

把补丁文件放进 `presets/clearai/`,旧形态下 `agent.cordis.yml` 坐在同一个目录——**两类基准都不需要改一个字**。这是本设计里风险最低的一步:不引入任何新的路径表达式。

(`baseUrl` 在声明行里的确切基准值尚未直接观测到——宿主在**会话选用该预设时**才挂载子插件,而探针里那些 `!!js` 在 boot 阶段不求值。采用同构布局后,基准是 `presets/clearai/` 或 `presets/` 两种可能中的哪一种都不影响结果:相对 name 与 `new URL('skills/', baseUrl)` 都会落在包内正确位置。**这条由实施后的端到端验证负责证伪**。)

### Q2 plugins 的内容怎么来

**构建期生成:唯一源是 `preset/agent.cordis.yml`,不在仓库里手写第二份。**

理由与 `build-package.mjs` 开头那条纪律完全一致:「包 = 源的一个纯函数」「手抄 = 第二本账。源改了、包没跟上,而两边的测试都绿」。`agent.cordis.yml` 有 304 行、18 个顶层行,手抄一份声明行必然漂移。

实现:`tools/build-package.mjs` 增加一步——读 `preset/agent.cordis.yml` 原文,**逐行缩进 6 格**后作为 `config.plugins` 的块标量内容嵌入;name/description 从 `preset/preset.yml` 读入。产出 `dist/clearai-dsh/presets/clearai/clearai.patch.yml`。

缩进嵌入是安全的:`!!js` 表达式、块标量(`|-`)、`cordis:group` 行都只是 YAML 文本,整体平移缩进不改变语义。

### Q3 name / description / order 从哪来

- `name` / `description`:读 `preset/preset.yml`(已有中英并排的一句话;它的注释解释了为什么 `description` 必须是块标量——那条约束在新形态下**照旧成立**,因为名册对读失败依然是静默降级成「没有元数据」)。
- `order`:定 **10**。内置四个是 standard=1 / ptc=2 / minimal=3 / cordis=4(见 dsh-web-app 的 `presets/*.patch.yml`),取 10 留出间隙,且不与将来新增的内置冲突。
- 发行物里**仍然保留** `presets/clearai/preset.yml`:它是人类可读的元数据源,`clearai-dsh seed` 也读它。宿主在新机制下不再读它,这一点写进 `verify-package.mjs` 的断言注释。

### Q4 template 与 skills 归谁消费

| 目录 | 消费者 | 机制换代后是否变化 |
|---|---|---|
| `preset/skills/`(clearai-loop) | 预设内 `skill-filesystem` 行的 `customSkillDirs` | **不变**,靠同构布局保住基准 |
| `preset/template/`(project.md、技能、memory、knowledge) | 内核插件缺省读 `../template`(见 `build-package.mjs` 装配表) | **不变**,与名册机制无关 |
| `presets/clearai/agent.cordis.yml` | 旧机制的名册扫目录用;**新机制下无人消费** | 保留:人类可读 + 历史痕迹,但不再是生效路径 |

## 二、两代宿主能否共用一个包:**不能**(假设 h-l9tsms 被推翻)

实测三条:

| 实验 | 结果 |
|---|---|
| 旧宿主 0.1.5-rc.1 + **干净 profile**(对照组) | ✅ 正常 boot |
| 旧宿主 + **数组**形式的 `dsh.bundle.patch` | ❌ 直接崩:`loadProfileDirectory` → `path.join` 收到 Array → `ERR_INVALID_ARG_TYPE`(dsh-app-boot/lib/index.js:853) |
| 旧宿主 + 字符串 patch + `preset-clearai` 行 | ❌ boot 失败:`Cannot find package '@deepseek-ai/dsh-agent-preset'`(旧宿主没有这个包) |
| 新宿主 0.1.7-rc.2 + 字符串 patch | ✅ 正常(dump 里能查到 `preset-probe`) |
| 新宿主 0.1.7-rc.2 + 数组 patch | ✅ 正常 |

**结论:0.2.4 支持边界 = 宿主 ≥ 0.1.7-alpha.1。** 旧宿主上 0.2.4 会让 profile **起不来**(比旧版的「预设不可见」更严重),所以:

1. CHANGELOG 与 README 必须显著声明这个边界(不是脚注);
2. Release 说明里带上同一句。

不写桥接插件去凑双兼容:那需要我们自己提供一个 `inject: ['agentPresets']` 的中间插件,在旧宿主上永久 pending、在新宿主上转发注册——复杂度与风险都远超这次适配本身,而旧宿主已经是过去时。

## 三、`dsh.bundle.patch` 用数组还是字符串

**用数组**:`["./cordis.patch.yml", "./presets/clearai/clearai.patch.yml"]`。

新宿主两种都接受(实测),但数组是宿主当前形态(web-app 自己就是数组 + 每预设一个文件),也为将来再加补丁文件留位。既然旧宿主无论如何都不支持 0.2.4,没有理由再迁就字符串。

## 四、验收怎么改

**现有 ④/④′ 为什么必须换掉:**它们断言组合里 `includeShippedRoot: true` 与名册 root 指向 `node_modules/clearai-dsh/presets/`。新机制里这两个键都**不存在**了,断言成了对已消失机制的考古。

**换成分档断言:**

- 旧机制宿主(`agent-presets` 行在组合里):保留原 ④/④′,原样判定。
- 新机制宿主(`agent-preset-registry` 行在组合里):
  - **④-new**:组合里存在 `id: agent-preset-registry` 行;
  - **④′-new**:组合里存在 `id: preset-clearai` 声明行,且 `config.id = clearai`、`config.plugins` 非空、`name`/`description`/`order` 齐备;
  - **④″-new**:声明行里 `plugins` 的每一个 `name` 都能解析——包名型去 profile 的 `node_modules` 里解析,相对路径型按「patch 文件目录 + 相对名」检查文件存在。
- **运行态(可选但强烈建议)**:起一次 profile,断言启动输出里没有 preset 加载失败。

**一个必须写进断言注释的反面教训:**探针已证实——**preset 里放一个根本不存在的插件,boot 依然完全正常**。因为子插件挂载推迟到会话真正选用该预设时(`agentPresets.register()` 只登记定义,eager 的是定义本身)。所以「启动无错」**不能**单独当作「预设可用」的证据,它只能证明「profile 没被这条声明行弄坏」。

**「模式选择器里真的出现 ClearAI」由一次真实环境端到端来证:**把本机 dsh 升到最新(或直接用 0.1.7-rc.2 起 profile)、装入适配后的包,在界面上确认 ClearAI 出现在预设选择器里。这一步在 CI 里做不到(没有模型凭据 → 无法创建会话来触发挂载),所以它是**发布前的一次人工/本地确认**,结论写进发布报告。
