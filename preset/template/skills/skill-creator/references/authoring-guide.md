## 1. description 写法与"pushy"度

description 是 Skill 触发的唯一依据。模型只看 name+description 决定要不要加载本 skill。两个常见失败：
- **欠触发**（更常见）：该用时不用。对策是把描述写得主动——显式列触发场景，并加一句"即使用户没明说要用本技能，只要涉及 X/Y/Z 就用"。
- **过触发**：不该用时也用。对策是写清"不适用"并指向更合适的 skill。

把握度：宁可稍微 pushy 一点纠正欠触发，但用"不适用"兜住边界。

## 2. 触发词怎么选

放进 `【阶段·触发词: ...】` 的词，应是**用户真实任务文本里会出现**的词，而非你对该领域的术语。想象用户会怎么口语化地描述这个需求：
- 包含同义/近义说法（正式的、口语的）。
- 包含用户**不点名**本 skill、但显然需要它的场景词。
- 3-6 个即可，过多稀释。

## 3. 好例 / 坏例

**description 坏例**（太被动、无触发场景）：
> 引用管理：检索论文元数据，DOI 转 BibTeX。

**好例**（主动 + 触发场景 + 边界）：
> 【引用管理·触发词: 引用, 参考文献, BibTeX, DOI, 文末引用, 去重】检索论文元数据、DOI→BibTeX、校验去重。适用：预研/综述报告文末引用统一、交付前引用准确性检查。不适用：全文综述撰写（用 literature-review）。

## 4. 适用 / 不适用 的写法

- **适用**：列 2-4 个该 skill 最该上场的具体情境。
- **不适用**：列易混淆的邻近情境，并**指向应该用的 skill 名**。这既减少误触发，也帮模型在多 skill 竞争时选对。

## 5. 输出格式与示例模式

要求固定产出格式时，直接在正文给模板：
```markdown
## 报告结构（严格按此）
# 标题
## 摘要
## 关键发现
## 建议
```

给示例帮助很大，用 输入→输出 对照：
```markdown
**示例 1**
输入：为用户认证加了 JWT
输出：feat(auth): 实现基于 JWT 的认证
```

## 6. 何时该 bundle 脚本

读你自己几次任务的过程记录：如果**多次**都独立写了类似的 `create_docx.py` / `build_chart.py` / 同样的多步处理，这是强信号——把它写一次放进该 skill 的 `scripts/`，正文里指明"用 scripts/xxx.py 而非每次重写"。每个未来调用都省掉重造轮子。

ClearAI 里脚本由 bash 工具执行，写类动作由系统策略治理。脚本要自带用法注释、参数清晰、可独立运行。

## 7. 多领域拆分

一个 skill 覆盖多领域/框架时，按变体拆 `references/`，正文只做选择与编排：
```
cloud-deploy/
├── SKILL.md         # 工作流 + 如何选变体
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
模型只读相关那一个变体文件，省 context。大参考文件（>300 行）开头放目录。

## 8. 自检清单（写完回看）

- [ ] description 首行有 `【阶段·触发词: ...】`，词是用户会说的话。
- [ ] 写了"适用 / 不适用"，不适用指向了别的 skill。
- [ ] 主动度够（不会欠触发），但有边界（不会过触发）。
- [ ] 正文是祈使句、解释了 why、没堆大写 MUST。
- [ ] SKILL.md 主干精简（<500 行），长内容挪进 references/ 并留指针。
- [ ] 重复出现的脚本已 bundle 进 scripts/。
- [ ] name 是 kebab-case；frontmatter 只含允许的 key。
- [ ] 评测交给收件箱（人评）+ uses/wins（量化），没有另造评测机器。
